Rocket Auth est la brique d'identité du Middleware Rocket : un **fournisseur OpenID Connect** (SSO). Il sert à la fois :

- de **compte unique** : vos collaborateurs se connectent une fois, avec leur compte local ou leur mot de passe d'annuaire, puis passent d'une application à l'autre sans se reconnecter ;
- de **serveur d'autorisation** : les autres briques Rocket (Rocket Mailer, Rocket Cloud, Rocket Print, Rocket Doc Fusion) et vos propres applications délèguent leur connexion à Rocket Auth et reçoivent l'identité, l'adresse et les groupes de l'utilisateur.

## Architecture

| Élément | Technologie | Rôle |
|---|---|---|
| API | Symfony 8, API Platform 5, PostgreSQL | Comptes, clients OAuth, points d'accès OpenID Connect, jetons, consentements |
| Worker | Symfony Messenger et Scheduler | Vérifications périodiques de l'annuaire et des fournisseurs, tâches de fond |
| Front | Nuxt 4, Nuxt UI 4 | Connexion, page d'autorisation, déconnexion, applications autorisées, administration |
| Documentation | Nuxt Content | Ce site, et le changelog |

Rocket Auth partage sa stack et son socle (comptes, LDAP, SSO, applications, tableau de bord, mises à jour) avec les autres briques Rocket : Rocket Mailer, Rocket Cloud, Rocket Print et Rocket Doc Fusion. Ce socle vient de [rocket-core](https://github.com/fayouz/rocket-core).

## Cycle d'une connexion

1. L'utilisateur ouvre une application (par exemple Rocket Print). Elle le redirige vers `/oauth/authorize` de Rocket Auth, avec son client ID, son adresse de retour, les scopes demandés, un `state`, un `nonce` et un défi PKCE.
2. Rocket Auth affiche sa page de connexion si l'utilisateur n'a pas de session, puis la **page d'autorisation** : ce que l'application demande (identité, nom, adresse, groupes…). Une application **de confiance**, ou déjà autorisée, n'affiche pas cette page.
3. Le navigateur revient sur l'application avec un **code** à usage unique, valable 60 secondes.
4. Le serveur de l'application échange ce code contre des jetons sur `/oauth/token` : un jeton d'accès, un **jeton d'identité** signé (RS256) et un jeton de rafraîchissement.
5. L'application vérifie le jeton d'identité avec les clés publiées sur `/oauth/jwks`, et ouvre sa propre session.
6. À la déconnexion, l'application renvoie vers `/oauth/logout` : la session Rocket Auth se termine, et le navigateur revient sur l'application.

Voir [OpenID Connect](/api/openid-connect) pour le détail de chaque étape.

## Sécurité

- Les secrets des clients ne sont stockés que sous forme de hash ; ils ne sont affichés qu'une fois, à la création ou à la régénération.
- Les applications publiques (navigateur, mobile) doivent utiliser PKCE (S256). Les adresses de retour et de déconnexion doivent être déclarées à l'avance, à l'identique.
- Un code présenté deux fois, ou un jeton de rafraîchissement déjà utilisé, révoque tous les jetons de l'utilisateur pour cette application.
- Les jetons émis pour les applications sont signés par une clé distincte de celle des sessions Rocket Auth : un jeton d'accès ne peut jamais servir à se connecter à Rocket Auth.

## Traçabilité

Chaque connexion à Rocket Auth, chaque autorisation accordée à une application et chaque refus sont enregistrés, avec l'utilisateur et l'application. Toutes les entités enregistrent leur date et leur auteur de création et de modification (`createdAt`, `createdBy`…), et chaque client garde sa date de dernière utilisation.
