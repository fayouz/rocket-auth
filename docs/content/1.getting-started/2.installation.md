## Avec Docker Compose

::steps{level="3"}

### Démarrer la stack

```bash [Terminal]
docker compose up -d --build
```

Cela lance PostgreSQL, l'API (qui applique les migrations au démarrage), le worker et le front. Au premier démarrage, l'API génère ses clés : celles des sessions (JWT) et la **clé RSA qui signe les jetons OpenID Connect** (`app:oidc:generate-key`), dans le volume `jwt_keys`.

### Créer le compte administrateur

Ouvrez http://localhost:3100. Tant qu'aucun compte n'existe, Rocket Auth affiche la page **Configuration initiale** : nom, email et mot de passe (12 caractères minimum) de l'administrateur. La page n'est plus jamais accessible ensuite.

::warning
Tant que le compte n'est pas créé, la première personne qui ouvre l'application peut le créer. Si l'instance est accessible par d'autres avant que vous la configuriez, définissez `SETUP_TOKEN` : la page demandera ce jeton.
::

Vous pouvez aussi créer l'administrateur en ligne de commande :

```bash [Terminal]
docker compose exec api php bin/console app:user:create admin@exemple.com 'un-mot-de-passe-long' --admin
```

### Déclarer les applications

Dans **Administration → Clients OAuth**, créez un client par application qui connecte ses utilisateurs avec Rocket Auth. Voir [Clients OAuth](/administration/clients) et, pour les briques Rocket, [Brancher la suite Rocket](/administration/suite).

::

| Adresse | Contenu |
|---|---|
| http://localhost:3100 | Rocket Auth : connexion, autorisation, administration |
| http://localhost:8100/.well-known/openid-configuration | Document de découverte OpenID Connect |
| http://localhost:8100/api/docs | Documentation OpenAPI de l'API |

## L'émetteur (issuer)

L'**émetteur** est l'adresse publique de Rocket Auth pour les applications : il figure dans chaque jeton (`iss`), et les applications lisent `<émetteur>/.well-known/openid-configuration`. Il se règle avec `OIDC_ISSUER` et ne doit plus changer une fois les applications branchées.

- Par défaut, c'est l'adresse de l'API (`http://localhost:8100`).
- Le front relaie aussi `/.well-known/…` et `/oauth/…` vers l'API. Avec une seule adresse publique (proxy inverse, Codespaces), l'émetteur peut donc être l'adresse de l'interface, par exemple `https://auth.exemple.com`.

Les pages d'autorisation et de déconnexion font partie de l'interface : `/oauth/authorize` et `/oauth/logout` redirigent vers `FRONTEND_URL`, avec les mêmes paramètres.

## Images Docker

La CI publie deux images sur GitHub Container Registry, pour `main`, `develop` et les tags `vX.Y.Z` :

- `ghcr.io/fayouz/rocket-auth-api` : API, et aussi le worker, avec la commande `php bin/console messenger:consume async scheduler_default` ;
- `ghcr.io/fayouz/rocket-auth-front` : front Nuxt.

Leur version (`git describe --tags`) s'affiche dans l'application. Pour les mettre à jour depuis l'interface, voir [Mises à jour](/administration/updates).

::warning
Montez `config/jwt` dans un volume persistant (volume `jwt_keys`) : il contient la clé de signature OpenID Connect. Si elle est perdue ou régénérée, tous les jetons déjà émis deviennent invalides et les utilisateurs doivent se reconnecter aux applications.
::

## Configuration

### API

| Variable | Rôle | Défaut |
|---|---|---|
| `DATABASE_URL` | Connexion PostgreSQL | — |
| `APP_SECRET` | Secret Symfony | — |
| `JWT_PASSPHRASE` | Passphrase des clés des sessions Rocket Auth (`config/jwt/`, à monter en volume) | — |
| `OIDC_ISSUER` | Émetteur OpenID Connect : l'adresse publique de Rocket Auth pour les applications | `http://localhost:8100` |
| `FRONTEND_URL` | Adresse publique de l'interface, qui porte les pages d'autorisation et de déconnexion | `http://localhost:3100` |
| `OIDC_PRIVATE_KEY` | Clé RSA qui signe les jetons (RS256), générée au premier démarrage | `config/jwt/oidc-private.pem` |
| `OIDC_ACCESS_TOKEN_TTL` | Durée de vie des jetons d'accès (secondes) | `900` |
| `OIDC_ID_TOKEN_TTL` | Durée de vie des jetons d'identité (secondes) | `3600` |
| `OIDC_REFRESH_TOKEN_TTL` | Durée de vie des jetons de rafraîchissement (secondes), renouvelés à chaque usage | `2592000` (30 jours) |
| `MESSENGER_TRANSPORT_DSN` | File des tâches de fond | `doctrine://default` |
| `DATA_DIR` | Données écrites par l'application (vérifiées sur le tableau de bord) | `var/data` |
| `SECRETS_ENCRYPTION_KEY` | Clé de chiffrement des secrets en base (mot de passe de l'annuaire, secrets des fournisseurs OpenID Connect externes). Vide : dérivée de `APP_SECRET`. La changer oblige à ressaisir ces secrets. | — |
| `CORS_ALLOW_ORIGIN` | Origines autorisées à appeler `/api` depuis un navigateur (regex). Les points d'accès OpenID Connect (`/oauth/…`, `/.well-known/…`) acceptent toutes les origines. | localhost |
| `SETUP_TOKEN` | Jeton demandé par la page de configuration initiale | — |
| `UPDATE_REPOSITORY` | Dépôt GitHub dont les nouvelles versions sont signalées. Voir [Mises à jour](/administration/updates). | `fayouz/rocket-auth` |
| `UPDATER_TOKEN` | Active la mise à jour en un clic, avec le service `updater` (profil `updater`) | — |
| `RUN_MIGRATIONS` | `1` pour appliquer les migrations au démarrage du conteneur | `0` |

Les variables LDAP sont décrites dans [Utilisateurs et LDAP](/administration/users-ldap).

Pour remplacer la clé de signature (clé compromise, par exemple) :

```bash [Terminal]
docker compose exec api php bin/console app:oidc:generate-key --rotate
```

Les jetons signés avec l'ancienne clé cessent aussitôt d'être acceptés.

### Tâches planifiées

Le worker (`messenger:consume async scheduler_default`) vérifie lui-même, toutes les 5 minutes, l'annuaire LDAP et les fournisseurs OpenID Connect externes.

Avec LDAP, planifiez aussi la synchronisation de l'annuaire :

```bash [crontab]
*/30 * * * *  docker compose exec -T api php bin/console app:ldap:sync
```

### Front

| Variable | Rôle |
|---|---|
| `NUXT_PUBLIC_API_BASE` | URL de l'API vue par le navigateur. **Vide** : le front relaie `/api` vers l'API (une seule URL publique, pas de CORS). |
| `NUXT_API_INTERNAL_BASE` | URL de l'API vue par le serveur du front, ex. `http://api:80` |

::warning
En production, changez `APP_SECRET` et `JWT_PASSPHRASE`, montez les clés dans un volume persistant et servez le front et l'API en **HTTPS** : les codes, les secrets des clients et les jetons transitent par ces adresses.
::
