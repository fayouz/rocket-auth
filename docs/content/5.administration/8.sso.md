Rocket Auth peut lui-même déléguer la connexion à un fournisseur **OpenID Connect** externe : Entra ID, Keycloak, Google Workspace… Sa page de connexion affiche alors un bouton **Se connecter avec …** pour chaque fournisseur actif. Les comptes locaux et LDAP continuent de fonctionner.

Les applications branchées sur Rocket Auth n'y voient aucune différence : elles reçoivent toujours les jetons de Rocket Auth, avec l'identité, l'adresse et les groupes du compte.

::note
Pour l'inverse, connecter une application **à** Rocket Auth, voir [Clients OAuth](/administration/clients) et [Brancher la suite Rocket](/administration/suite).
::

## Déclarer Rocket Auth chez le fournisseur

Créez un client **confidentiel** avec le flux *authorization code* :

| Paramètre | Valeur |
|---|---|
| URL de retour (redirect URI) | `https://auth.exemple.com/auth/callback` (l'adresse de l'interface de Rocket Auth) |
| Scopes | `openid email profile`, plus `groups` pour récupérer les groupes et gérer les administrateurs depuis le fournisseur |
| PKCE | S256 (toujours envoyé par Rocket Auth) |

Notez le *Client ID* et le secret.

## Ajouter le fournisseur dans Rocket Auth

**Administration → Serveurs d'authentification → Ajouter un serveur → OpenID Connect**, puis :

- **Émetteur (issuer)** : l'URL publique du fournisseur. Son document de découverte est lu sur `<émetteur>/.well-known/openid-configuration`.
- **Client ID** et **secret**. Le secret est chiffré en base (`SECRETS_ENCRYPTION_KEY`) et n'est jamais renvoyé par l'API.
- **Groupe administrateurs** (optionnel) : un utilisateur dont la revendication `groups` contient cette valeur reçoit le rôle administrateur de Rocket Auth, et le perd sinon. Laissez vide pour gérer les administrateurs dans Rocket Auth.
- **URL interne** (optionnel) : l'adresse du fournisseur vue depuis l'API quand elle diffère de l'émetteur, par exemple dans un réseau Docker.
- **Relier les comptes existants de même email** : à réserver à un fournisseur de confiance. Sans cette option, une connexion est refusée si un compte local ou LDAP utilise déjà la même adresse.

Le bouton **Tester la connexion** lit le document de découverte avant l'enregistrement.

## Ce qui se passe à la connexion

1. L'interface redirige vers le fournisseur avec `state`, `nonce` et un défi PKCE (S256), gardés dans l'onglet.
2. Au retour sur `/auth/callback`, elle transmet le code à l'API (`POST /api/auth/oidc/callback`).
3. L'API échange le code avec le secret du client, puis vérifie la signature du jeton d'identité (RS256, clés JWKS), l'émetteur, l'audience, l'expiration et le `nonce`.
4. Le compte est retrouvé par son identifiant chez le fournisseur (`sub`), ou créé à la première connexion (source « SSO »). Prénom, nom, adresse et groupes suivent le fournisseur.
5. L'API ouvre une session Rocket Auth, comme une connexion par mot de passe. Si la connexion avait commencé depuis une application, l'utilisateur y retourne ensuite.

Un compte SSO ne peut pas se connecter par mot de passe. Pour le bloquer, désactivez-le dans **Utilisateurs** : il ne peut plus se connecter ni à Rocket Auth ni aux applications. Supprimer le serveur peut aussi désactiver tous ses comptes.

## Supervision

Le worker vérifie chaque fournisseur actif toutes les 5 minutes (document de découverte). Le tableau de bord affiche le résultat dans **Authentification unique**.

## API

| Méthode | Chemin | Accès |
|---|---|---|
| `GET` | `/api/auth/providers` | public : fournisseurs actifs (nom, point d'autorisation, client ID, scopes) |
| `POST` | `/api/auth/oidc/callback` | public : `{ provider, code, codeVerifier, redirectUri, nonce }` → `{ token }` |
| `POST` | `/api/authentication_servers/oidc/test` | administrateur : `{ url, internalUrl }` |
| `GET`, `POST`, `PATCH`, `DELETE` | `/api/authentication_servers` | administrateur (`type: "oidc"`, `clientId`, `clientSecret`, `scopes`, `internalUrl`, `adminGroupDn`, `linkExistingAccounts`) |
