Rocket Auth est un fournisseur **OpenID Connect** standard : toute bibliothèque compatible s'y branche avec l'émetteur, un client ID et, pour une application serveur, un secret. Les clients se déclarent dans [Clients OAuth](/administration/clients).

Les exemples utilisent l'émetteur `https://auth.exemple.com` (`OIDC_ISSUER`, voir [Installation](/getting-started/installation#lémetteur-issuer)).

## Découverte

```bash [Terminal]
curl https://auth.exemple.com/.well-known/openid-configuration
```

| Élément | Valeur |
|---|---|
| `authorization_endpoint` | `<émetteur>/oauth/authorize` |
| `token_endpoint` | `<émetteur>/oauth/token` |
| `userinfo_endpoint` | `<émetteur>/oauth/userinfo` |
| `jwks_uri` | `<émetteur>/oauth/jwks` |
| `revocation_endpoint` | `<émetteur>/oauth/revoke` |
| `end_session_endpoint` | `<émetteur>/oauth/logout` |
| Scopes | `openid`, `profile`, `email`, `groups`, `offline_access` |
| Flux | `authorization_code`, `refresh_token`, `client_credentials` ; `response_type=code` uniquement |
| Authentification du client | `client_secret_basic`, `client_secret_post`, `none` (client public) |
| PKCE | `S256` |
| Signature des jetons | `RS256` |
| `prompt` | `none`, `login`, `consent`, `select_account` |
| `backchannel_logout_supported`, `backchannel_logout_session_supported` | `true` : jetons de déconnexion envoyés aux applications, avec `sid` (voir [Déconnexion back-channel](#déconnexion-back-channel)) |

Les points d'accès `/oauth/…` et `/.well-known/…` répondent à toutes les origines (CORS), pour les applications qui tournent dans le navigateur.

## Autorisation

L'application envoie le navigateur sur `/oauth/authorize` :

```text
https://auth.exemple.com/oauth/authorize
  ?response_type=code
  &client_id=rocket-print
  &redirect_uri=https://print.exemple.com/auth/callback
  &scope=openid email profile groups
  &state=…
  &nonce=…
  &code_challenge=…&code_challenge_method=S256
```

| Paramètre | Règle |
|---|---|
| `client_id` | Client connu et actif |
| `redirect_uri` | Exactement une des adresses de retour du client. Facultatif si le client n'en a qu'une. |
| `scope` | Obligatoire, parmi les scopes autorisés pour le client |
| `code_challenge` | PKCE en `S256`. **Obligatoire pour un client public**, recommandé pour tous. |
| `state`, `nonce` | Renvoyés tels quels (`state` dans la redirection, `nonce` dans le jeton d'identité) |
| `prompt` | `none` : jamais de page, erreur `login_required` ou `consent_required` si besoin ; `login` ou `select_account` : nouvelle connexion ; `consent` : toujours demander l'accord |

Rocket Auth connecte l'utilisateur, lui demande son accord si nécessaire (voir [Se connecter aux applications](/account/sign-in#la-page-dautorisation)), puis renvoie le navigateur :

```text
https://print.exemple.com/auth/callback?code=…&state=…&iss=https://auth.exemple.com
```

Le code est à usage unique et valable **60 secondes**. En cas d'erreur, la redirection porte `error` et `error_description` (`access_denied`, `invalid_scope`, `unauthorized_client`…). Une application inconnue ou une adresse de retour non déclarée n'est jamais redirigée : l'erreur s'affiche dans Rocket Auth.

## Jetons

`POST /oauth/token`, en `application/x-www-form-urlencoded`. Le client s'authentifie en HTTP Basic (`client_id:secret`) ou avec `client_id` et `client_secret` dans le corps ; un client public n'envoie que `client_id`.

### Code d'autorisation

```bash [Terminal]
curl -X POST https://auth.exemple.com/oauth/token \
  -u "rocket-print:ras_…" \
  -d grant_type=authorization_code \
  -d code=… \
  -d redirect_uri=https://print.exemple.com/auth/callback \
  -d code_verifier=…
```

```json
{
  "access_token": "<jwt>",
  "token_type": "Bearer",
  "expires_in": 900,
  "scope": "openid email profile groups",
  "id_token": "<jwt>",
  "refresh_token": "rar_…"
}
```

`redirect_uri` doit être celle de la demande d'autorisation, et `code_verifier` correspondre au défi PKCE. Un code présenté une seconde fois est refusé, et tous les jetons de l'utilisateur pour ce client sont révoqués.

### Jeton de rafraîchissement

```bash [Terminal]
curl -X POST https://auth.exemple.com/oauth/token \
  -u "rocket-print:ras_…" \
  -d grant_type=refresh_token \
  -d refresh_token=rar_…
```

Chaque usage renvoie un **nouveau** jeton de rafraîchissement et révoque l'ancien. Réutiliser un jeton déjà échangé révoque tous les jetons de l'utilisateur pour ce client. `scope` peut réduire les scopes, jamais les étendre. Durée de vie : `OIDC_REFRESH_TOKEN_TTL` (30 jours).

### Identifiants client

Pour une application qui agit pour elle-même, sans utilisateur (client confidentiel qui a le flux `client_credentials`, case **Identifiants client** de sa fiche) :

```bash [Terminal]
curl -X POST https://auth.exemple.com/oauth/token -u "mon-service:ras_…" -d grant_type=client_credentials
```

Le jeton d'accès a pour sujet (`sub`) le client ID et vaut **5 minutes** : l'application en redemande un. Il n'y a ni jeton d'identité ni jeton de rafraîchissement, et les scopes liés à un utilisateur (`openid`, `profile`, `email`, `groups`, `offline_access`) sont ignorés. Les deux authentifications du client fonctionnent (`client_secret_basic` ci-dessus, `client_secret_post` avec `client_id` et `client_secret` dans le corps).

#### Appeler une autre application (audience)

Pour appeler l'API d'une autre application (par exemple Rocket Cloud qui envoie un email par Rocket Mailer), le client précise son **audience** : le client ID de l'application appelée.

```bash [Terminal]
curl -X POST https://auth.exemple.com/oauth/token \
  -u "rocket-cloud:ras_…" \
  -d grant_type=client_credentials \
  -d audience=rocket-mailer
```

Le jeton porte alors `aud: "rocket-mailer"`, et `sub`, `azp`, `client_id` : `rocket-cloud`. L'audience doit être le client ID d'un client **actif** de Rocket Auth, sinon l'erreur est `invalid_target`. Sans `audience`, le jeton est destiné au client lui-même (`aud` = son client ID).

L'application appelée vérifie la signature (JWKS), l'émetteur, que `aud` est son propre client ID et l'expiration ; c'est elle qui décide quels clients peuvent l'appeler et avec quels droits. Les briques Rocket le font d'elles-mêmes : voir [Brancher la suite Rocket](/administration/suite#appels-entre-briques).

### Erreurs

Les erreurs suivent OAuth 2.0 : `{ "error": "…", "error_description": "…" }`, avec `invalid_client` (`401`), `invalid_grant`, `invalid_scope`, `invalid_target` (audience inconnue), `unauthorized_client` ou `unsupported_grant_type`.

## Contenu des jetons

Tous les jetons sont des JWT signés en **RS256**, avec les clés publiées sur `/oauth/jwks` (`kid` dans l'en-tête).

**Jeton d'identité** (scope `openid`), valable `OIDC_ID_TOKEN_TTL` (1 heure) :

| Revendication | Contenu |
|---|---|
| `iss`, `aud`, `azp` | L'émetteur ; le client ID |
| `sub` | Identifiant stable de l'utilisateur |
| `iat`, `exp`, `auth_time` | Émission, expiration, début de la session Rocket Auth |
| `nonce`, `at_hash` | Le `nonce` de la demande ; le hash du jeton d'accès |
| `sid` | La session Rocket Auth dans laquelle l'utilisateur s'est connecté à l'application (repris dans les jetons de déconnexion) |
| `name`, `given_name`, `family_name`, `preferred_username`, `updated_at` | Scope `profile` |
| `email`, `email_verified` | Scope `email`. Les adresses sont considérées comme vérifiées : les comptes sont créés par les administrateurs ou viennent de l'annuaire. |
| `groups` | Scope `groups` : les groupes de l'utilisateur (voir [Utilisateurs et LDAP](/administration/users-ldap#groupes)) |

**Jeton d'accès**, valable `OIDC_ACCESS_TOKEN_TTL` (15 minutes), 5 minutes pour les identifiants client : `iss`, `sub` (l'utilisateur, ou le client ID pour les identifiants client), `aud` (le client ID, ou l'audience demandée), `azp` et `client_id` (le client ID), `scope`, `token_use: "access"`, `iat`, `exp`, `jti`.

## Userinfo

```bash [Terminal]
curl https://auth.exemple.com/oauth/userinfo -H "Authorization: Bearer <jeton d'accès>"
```

```json
{
  "sub": "0199…",
  "name": "Alice Durand",
  "given_name": "Alice",
  "family_name": "Durand",
  "preferred_username": "alice@exemple.com",
  "email": "alice@exemple.com",
  "email_verified": true,
  "groups": ["rocket-admins"]
}
```

Les revendications dépendent des scopes du jeton. Un compte supprimé ou désactivé donne `401` (`invalid_token`). `GET` ou `POST`.

## Révocation

```bash [Terminal]
curl -X POST https://auth.exemple.com/oauth/revoke -u "rocket-print:ras_…" -d token=rar_…
```

Révoque un jeton de rafraîchissement du client (RFC 7009). Un jeton inconnu est accepté sans erreur. Les jetons d'accès ne se révoquent pas : ils expirent d'eux-mêmes.

## Déconnexion

L'application envoie le navigateur sur `/oauth/logout` (*RP-initiated logout*) :

```text
https://auth.exemple.com/oauth/logout
  ?client_id=rocket-print
  &post_logout_redirect_uri=https://print.exemple.com/login?logged_out=1
  &state=…
```

L'application se désigne par `client_id` ou par son jeton d'identité (`id_token_hint`). Rocket Auth termine sa session, puis renvoie vers `post_logout_redirect_uri` (avec `state`) seulement si cette adresse est déclarée pour le client ; sinon, il affiche **Vous êtes déconnecté**.

En terminant la session (depuis `/oauth/logout` ou le menu de Rocket Auth), Rocket Auth met fin aux connexions faites **dans cette session** : les jetons de rafraîchissement obtenus dans cette session sont révoqués, et les applications concernées reçoivent un jeton de déconnexion (ci-dessous). Les connexions faites depuis d'autres sessions (un autre navigateur, un autre appareil) restent ouvertes. Si la session Rocket Auth a déjà expiré dans ce navigateur, il n'y a plus rien à terminer côté Rocket Auth.

### Déconnexion back-channel

Rocket Auth implémente [OpenID Connect Back-Channel Logout 1.0](https://openid.net/specs/openid-connect-backchannel-1_0.html). Une application qui a une **URL de déconnexion back-channel** (`backchannel_logout_uri`, sur sa fiche dans [Clients OAuth](/administration/clients)) reçoit, de serveur à serveur, un `POST` en `application/x-www-form-urlencoded` avec `logout_token` :

- quand l'utilisateur se déconnecte de Rocket Auth : les applications où il s'est connecté pendant cette session, avec `sid` ;
- quand un administrateur **désactive** ou **supprime** son compte (ou que la synchronisation de l'annuaire le désactive) : toutes les applications où il s'est connecté, sans `sid` ; tous ses jetons de rafraîchissement sont révoqués.

Le jeton de déconnexion est un JWT signé en RS256 (clés de `/oauth/jwks`, en-tête `typ: "logout+jwt"`) :

| Revendication | Contenu |
|---|---|
| `iss`, `aud` | L'émetteur ; le client ID de l'application |
| `sub` | L'utilisateur (même valeur que dans le jeton d'identité) |
| `sid` | La session Rocket Auth terminée (absente : toutes les sessions) |
| `events` | `{"http://schemas.openid.net/event/backchannel-logout": {}}` |
| `iat`, `exp`, `jti` | Émission, expiration (2 minutes), identifiant unique |

L'application vérifie le jeton (signature, `iss`, `aud`, `events`, absence de `nonce`, `iat` récent, `jti` jamais vu), ferme les sessions de l'utilisateur et répond `200`. Les envois partent en arrière-plan (worker) ; une autre réponse que `2xx` ou une erreur réseau est retentée (3 fois, avec un délai croissant), puis le message rejoint la file des échecs (`failed`).

### Déclaration par une brique

Une brique de la suite déclare elle-même son URL de déconnexion back-channel, authentifiée comme son client (confidentiel) :

```bash [Terminal]
curl -X POST https://auth.exemple.com/oauth/suite/register \
  -u "rocket-print:ras_…" \
  -d backchannel_logout_uri=http://print-api/api/auth/oidc/backchannel-logout
```

```json
{ "client_id": "rocket-print", "backchannel_logout_uri": "http://print-api/api/auth/oidc/backchannel-logout", "grant_types": ["authorization_code", "refresh_token", "client_credentials"] }
```

Seule cette adresse peut être déclarée ainsi (une URL `http(s)` absolue, sans fragment ; vide pour l'effacer) ; tout le reste du client reste aux administrateurs. Les briques Rocket le font à la première connexion et avec `rocket:suite:sync`.

## Applications de la suite

```bash [Terminal]
curl https://auth.exemple.com/api/suite/apps
```

```json
{
  "apps": [
    { "id": "print", "name": "Rocket Print", "url": "https://print.exemple.com", "icon": "i-lucide-printer", "description": "…" }
  ],
  "account": "https://auth.exemple.com"
}
```

Public, mis en cache une minute. La liste contient les clients **actifs** qui ont une adresse d'application, triés par nom ; `id` est le client ID sans le préfixe `rocket-`. `account` est l'adresse de l'interface de Rocket Auth (`FRONTEND_URL`), cible du lien **Mon compte** des briques. C'est la source du sélecteur d'applications des briques en mode suite : voir [Brancher la suite Rocket](/administration/suite).

## Consentements

| Méthode | Chemin | Accès |
|---|---|---|
| `GET` | `/api/consents` | Utilisateur : ses propres autorisations (`clientName`, `clientDescription`, `scopes`, `grantedAt`, `lastUsedAt`). Les administrateurs aussi ne voient que les leurs. |
| `DELETE` | `/api/consents/{id}` | Utilisateur : retire l'accès et révoque les jetons de rafraîchissement de l'application |
